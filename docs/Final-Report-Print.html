Final Project Report: Conversational RAG System

Architecture, Technical Implementation, Evaluation & Performance Analysis in .NET 10
Technology Stack: .NET 10 | Clean Architecture | Qdrant Vector DB | Ollama (Gemma 2) | Groq Cloud | PdfPig

1. Executive Summary & Overview

1.1 Objective

The objective of this project was to design, develop, and benchmark a production-grade, conversational Retrieval-Augmented Generation (RAG) system built from first principles in .NET 10. Rather than relying on high-level orchestration abstractions (e.g., LangChain or Semantic Kernel) in initial phases, the system was implemented incrementally across 13 iterative sprints to achieve complete architectural transparency, rigorous separation of concerns, and full control over retrieval dynamics.

1.2 System Architecture

The system adheres strictly to Clean Architecture principles, ensuring that business and retrieval logic remain decoupled from external transport mechanisms and model providers:

src/
├── RagDemo.Domain           # Core abstractions, entity models, evaluation contracts
├── RagDemo.Application      # Pipeline orchestration, prompt engineering, query classification
├── RagDemo.Infrastructure   # Concrete implementations (Ollama, Groq, Qdrant, PdfPig)
├── RagDemo.Api              # Minimal APIs, Server-Sent Events (SSE) endpoints, middleware
└── RagDemo.Cli              # Interactive streaming terminal client

Core Architectural Pillars:

  • Dependency Inversion (SOLID): All orchestration workflows depend strictly on domain contracts (IChatCompletionService, IVectorStore, IRetriever, IEmbeddingGenerator, IConversationMemory).
  • Decoupled Pipelines: Document ingestion/indexing and query-time retrieval operate as completely independent subsystems.
  • Multi-Provider AI Abstraction: Config-driven switching between local execution (Ollama with Gemma 2 2B) and ultra-low-latency cloud acceleration (Groq with GPT-OSS-120B / Llama 3).

2. Technical Implementation

2.1 Data Extraction

  • Engine: PdfPig managed via PdfDocumentExtractor and PdfChunkProvider.
  • Text Reconstruction: Implemented layout-aware word-level reconstruction to eliminate whitespace coalescence across multi-column PDF layouts and hyphenated line breaks.

2.2 Chunking Strategy

  • Strategy: CharacterChunkingStrategy (ADR-017).
  • Configuration: Chunk Size = 1,000 characters; Overlap = 200 characters.
  • Validation: Tested across an academic corpus of 5 machine learning research papers (629 total chunks generated), maintaining semantic boundaries while preventing context fragmentation.

2.3 Embedding Generation

  • Model: nomic-embed-text (768-dimensional dense vectors) hosted on local Ollama.
  • Concurrency Control: Implemented an asynchronous pipeline with SemaphoreSlim(8) to maximize GPU/CPU utilization while guaranteeing local system stability.

2.4 Vector Database & Storage

  • Engine: Qdrant running in containerized Docker infrastructure with persistent storage volumes.
  • Distance Metric: Cosine Similarity on 768-dimensional vectors.
  • Payload Architecture: Every vector point stores rich provenance metadata (source filename, chunkIndex, and raw text content) for complete diagnostic attribution and auditability.

2.5 LLM Integration & Grounded Prompting

  • Local Inference: Local Ollama endpoint serving gemma2:2b.
  • Cloud Acceleration: Cloud Groq endpoint with built-in retry and exponential backoff.
  • Grounded Prompting (RagPromptBuilder): Enforces strict adherence to retrieved document context. Prompts mandate an explicit refusal token when information is missing:

    "I could not find the answer in the provided documents."

2.6 Conversational Memory

  • Memory Storage: Thread-safe InMemoryConversationMemory backed by ConcurrentDictionary.
  • Context Window: Sliding window over the last 4 dialogue turns (ConversationTurn).
  • History-Aware Retrieval: Previous dialogue turns are synthesized into the retrieval query to disambiguate conversational follow-ups without requiring redundant query-rewriting LLM calls.

3.2 Metrics & Scoring Methodology

  • Expected Source Coverage: Measures if the target ground-truth PDF was ranked in the retrieved Top-K set.
  • Keyword Coverage: Measures the percentage of essential domain concepts successfully present in the generated answer.
  • Grounding Accuracy (Faithfulness): Verifies 100% adherence to refusal rules when questions fall outside corpus boundaries.
  • Context Precision & Recall: Proportion of retrieved chunks that are strictly relevant vs. overall recall of ground truth knowledge.
  • Latency Diagnostics: Isolated telemetry measuring retrieval duration (T_retrieval in ms) from LLM generation time (T_gen in s).

4.2 Key Findings & Discussion

  • Retrieval Efficiency: Vector search across Qdrant consistently completed in ~140 ms, confirming that vector search scale is negligible compared to model inference.
  • Latency Mitigation: Local LLM generation was the sole latency bottleneck (43.0 s). This was mitigated via SSE token streaming (immediate perceived output) and cloud provider integration (1.6 s total turnaround, 96% latency reduction).
  • Zero Hallucinations: The system achieved 100% accuracy on refusal test cases (e.g., Question 12), rigorously adhering to grounded constraints.
  • Conversational Coherence: Multi-turn dialogues correctly resolved pronouns without degrading single-turn precision.

5. Conclusion

The project delivers a fully decoupled, extensible, and high-performing Conversational RAG solution in modern .NET 10. By pairing clean dependency-inverted design with persistent Qdrant vector storage, streaming SSE delivery, and grounded prompting, the system achieved 100% Context Recall, 100% Faithfulness, and 91.7% Answer Correctness.
